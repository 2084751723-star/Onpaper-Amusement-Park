本计划已进入实施阶段。2026-11-20 用户批准乙暂时不可参与期间的甲独立预开发规则，详见第 4.4 节；该批准立即允许限定范围的开发，不代表任何 PR 已审查、合并或 DONE。甲乙分别使用第 7 节的启动/继续提示词，人只负责启动/继续 AI、登录授权、必要的产品决定和可选的实体打印验收。

- 总交付目标：**2026 年 11 月 23 日前（北京时间）**。
- **不设置开工、提交、推送、合并或拉取的固定时刻。** 每一步只由任务完成情况、前置依赖和验收结果触发。
- 当前改动通过本地验证后，AI 立即提交并交接；下一任务的依赖满足就继续，不等另一个人到某个时刻。依赖不满足则在 GitHub 明确记录阻塞，优先做已解锁的独立任务，没有可执行任务才等待。总交付期限不能成为跳过验证的理由。

### 产品仅做这些

单主题“失落森林”、单玩法、两张基础布局及可复现变体：两人打开同一题号的不同角色链接，交流线索、标记路线、提交解答；同一题可以打印成两张独立 A4，答案页可选为第三页。

可解性：独立 DFS 必须找到且只找到一条完整解；去掉 B 线索后，A 地图至少存在两个可达终点。只对已验证布局做旋转、镜像、符号置换，同时变换方向规则。AI 负责写代码和文案，不代替规则验证。AI 浏览器测试不冒充真人趣味性验证。

### 2.4 每轮提交—推送—合并—拉取的固定流程

**作者 AI（甲乙都执行）**：
1. 开始常规任务：检查干净工作区 → `git fetch origin` → 本地 `main` 快进到远端 → 创建自己的任务分支。第 4.4 节的提前开发改用已记录、已验证的甲方提交作为基线，不要求该提交已合入 main。
2. 实现本任务 → 测试/构建 → 必要浏览器验证 → 检查差异 → 只暂存本任务文件 → 新建提交。
3. 推送自己的分支 → 用 `gh pr create` 创建面向 `main` 的 PR → 按格式交接。提前开发的堆叠 PR 按第 4.4 节先面向直接父分支创建 draft PR，不合并到父分支。每个通过验证的小里程碑即可提交，不能等截止前才攒成一个巨型提交。
4. 收到意见：仍在自己的分支修复，重新验证，新建提交并推送；更新交接证据。
5. 若 `main` 已前进：作者先确保无未提交改动，fetch 后将 `origin/main` merge 到自己的分支；解决冲突，重新测试并推送，不能 force push。

**审查与合并**：
- 甲的 PR 由乙 AI 审查；乙的 PR 由甲 AI 审查。审查在自己的干净副本临时检出待审 PR，只读检查/运行验证，不往对方分支提交；审查结束回到自己的分支。
- 甲确认检查对应当前 PR head、作者已吸收最新 `main`、没有冲突且验证通过，才使用 PR merge commit 合并。命令可用 `gh pr merge <实际PR号> --merge --match-head-commit <已核实headSHA>`，不加删除分支参数。
- 只对有真实依赖的 PR 先合提供接口/能力的一方；互不依赖的 PR 谁通过检查就可先合，不必等另一方一起完成。每次合并后，后续 PR 的作者都要吸收更新后的 `main` 并重新验证，即使没有文本冲突也不能省略。
- 单纯吸收已审查 `main` 且没有业务变化时，审查者可复核新增差异及新测试结果后重新给出当前 SHA 的通过记录；存在冲突解决或业务修改则重新审查。
- 合并后甲先完成相关主分支验收，再发包含 `DONE` 的 `SYNC`；失败则记录 `BLOCKED` 并修复，不解锁下游。任务 DONE 后，双方按各自依赖更新本地 `main`，下一任务从新分支开始，不继续用已合入分支。

干净工作区中新任务的示例（由 AI 执行，不要求人手工敲）：
```bash
git status --short
git remote -v
git fetch origin
git switch main
git pull --ff-only origin main
git switch -c feat/jia-puzzle-engine
```
乙换成自己的分支名。已有任务分支吸收更新使用 `git merge --no-edit origin/main`；不 rebase 已推送分支、不改写历史。任何命令失败先查原因，不自动升级为强制命令。

## 3. 甲-0 必须冻结的工程和接口

### 工程基线

React＋TypeScript＋Vite，静态输出 `dist/`；复用甲本机 Qoder Sites 官方 React starter，乙只使用仓库锁文件，不自行创建项目或另选框架。

既有仓库含 `LICENSE`，已核实官方空目录初始化脚本会拒绝它。甲克隆后应保留许可证和 `.git`，在原目录安全复制 starter 的缺失文件，先检查冲突，不删除 LICENSE 以绕过检查，也不建立第二个项目。保留来源/许可说明。

甲配置 Vitest 和 `test` 脚本，锁文件一起提交。初始化的 `.gitignore` 排除 `node_modules/`、`dist/`、`.env*`、私钥、`*.qoder.site` 及 `.qoder/design/` 本机状态；业务样式和公开游戏素材要提交。乙不得复制甲的本机 Sites 描述文件另建站点。

共同命令：`npm ci`（首次/锁文件变化时）、`npm run dev`、`npm run test -- --run`、`npm run build`、`npm run preview`。无 CI 时不能把本地测试称作 GitHub CI 通过。

### 模型约定

由甲落实到 [src/game/types.ts](../src/game/types.ts)，双方以该文件为准：
- `Coord` 使用 `{row, col}`，零起始；路径包含起点，合法长度等于线索数＋1。
- `Role` 为 `a | b`；符号固定四种：`leaf | moon | star | mushroom`；方向固定 `north | east | south | west`。
- `Puzzle` 含版本、种子、5×5格子、起点、有序线索；每条线索指定下一格符号，可有一个禁止方向；总计最多两条方向限制。
- `MapView` 只含 A 可见的地图、起点、步数、题号；`ClueView` 只含 B 的有序线索、步数、题号。
- `generatePuzzle(session)`、`getRoleView(puzzle, role)`、`validatePath(puzzle, path)`、`solvePuzzle(puzzle, limit=2)` 为共享引擎接口。
- 同一版本＋种子确定性生成；链接只带版本/种子/角色或打印模式，不带答案。种子统一为 6 位十六进制，读取时大写规范化；非法参数明确报错，不静默换题。

### 组件约定

甲-0 固定实际 props 类型和可构建的最小组件接口，之后由乙实现；名字变化必须先经双方在 PR 确认。
- `GameSetup`：接收题号、两角色链接和新局/选择角色/打印回调。
- `RolePanel`：接收角色及对应投影、A 的路径和选格/撤销/清空/提交回调、提交状态；B 不展示共享进度。
- `PuzzleMap`：接收 `MapView`、路径、可选选格回调、打印模式；屏幕与纸面复用同一地图数据。
- `PrintPages`：接收地图投影、线索投影和显式可选答案；默认仅 A/B 两页，不默认渲染隐藏答案。

**甲-0 必须由甲在 App 预接可操作的角色样例入口、路径状态、选格/撤销/清空回调，以及含可选答案数据的打印预览入口。** 乙检出基线后，仅修改自己的组件即可在浏览器独立测试角色交互和打印，不需要修改 App，也不必先等自己的 PR 合入才能验证。样例提交明确显示“正式验题待接入”，不能假报解题成功；样例答案只供排版，不作为规则正确性的证明。

这些入口和数据明确标为开发样例。甲-1 独立求解通过后才有正式题目，甲-1I/甲-4负责接入正式引擎与全部入口；最终删除或替换开发样例接线，完成品不得残留假验证或样例代替正式逻辑。

### 甲-0 实际接口与样例入口

以下记录工程实现契约，不代表甲-0 已审查、合并或 DONE：

- 共享类型与组件 props 统一从 `src/game/types.ts` 导入；业务组件使用命名导出。官方 UI 原语仍位于根目录 `components/ui/`，`@/` 指向仓库根目录，不能与乙负责的 `src/components/` 混淆。
- `Cell` 为 `{kind: "obstacle"}` 或 `{kind: "symbol", symbol: SymbolId}`；地图为只读二维数组。`MapView` 字段为 `puzzleId/grid/start/stepCount`；`ClueView` 字段为 `puzzleId/clues/stepCount`。
- `GameSetupProps` 使用 `puzzleId/roleLinks/onNewGame/onSelectRole/onPrint`；`PuzzleMapProps` 使用 `view/path/onSelectCell?/printMode?`。
- `RolePanelProps` 是以 `role` 判别的联合：A 接收 `view/path/onSelectCell/onUndo/onClear/onSubmit/submission`；B 只接收 `view`，没有路径、提交状态或回调。
- `PrintPagesProps` 使用 `mapView/clueView/answer?`；未显式传入 `answer` 时，答案页不得出现在 DOM。路径坐标始终零起始且包含起点，仅显示文字转换为从 1 开始。
- `PuzzleEngine` 仅冻结四个引擎函数的 TypeScript 签名；甲-0 不提供假实现。正式实现、独立求解与唯一性证明仍属于甲-1。
- 根路径为样例入口；角色 URL 使用 `?v=1&seed=D00001&role=a`（或 `b`）；打印使用 `?v=1&seed=D00001&mode=print`。大小写种子规范化；甲-0 仅识别 `D00001/D00002` 两个开发样例编号，不接受其他种子并冒充正式出题。
- “切换开发样例”仅切换编号并重置本端样例状态，两编号复用同一布局以便乙验证状态隔离；不代表甲-2 已有两个正式模板。刷新恢复、随机新局与正式种子链接仍属于后续任务。
- 开发样例在 `src/game/devSample.ts`，App 已预留选格、撤销、清空、提交与可选答案打印入口。样例路径只用于交互和排版，不证明可解性；提交始终显示“正式验题待接入”。
- 本地命令沿用 `npm ci`、`npm run dev`、`npm run test -- --run`、`npm run build`、`npm run preview`；补充 `npm run typecheck`。没有配置 GitHub CI。

## 4. 任务完成条件与下一步触发规则

### 4.1 什么才算任务完成

有代码或文档改动的任务必须同时满足：
1. 作者已实现本任务并完成要求的本地测试/构建/浏览器或文档检查；
2. 作者自己 commit、push、创建 PR，对方已检查当前 head；
3. 甲已将通过检查的 PR 合入 `main`；
4. 合入后的相关验收通过，甲在同步线程记录 `DONE`、实际 main SHA 和被解锁任务。

**“写完”“本地测试通过”“已经推送”“PR 已打开”都不等于任务完成。** PR 已合入但集成验收失败时，状态仍为阻塞，相关下游不得启动；先修复并重验。纯克隆检查、审查、发布或验收任务以真实证据和完成记录为准，没有文件改动就不制造空提交/空 PR。

任务状态：`待开始 → 开发中 → READY_FOR_REVIEW → 已合入待验收 → DONE`；审查或验收失败转为 `BLOCKED/需修改`，修复后重新检查。作者继续处理自己的 PR，不能把失败任务标成 DONE 来解锁下一项。

### 4.2 何时提交、推送、合并、拉取

| 动作 | 唯一触发条件 |
|---|---|
| 提交 | 一个可验证的小改动已完成，相关检查通过，暂存内容确认只含本任务文件 |
| 推送与建 PR | 本任务可供对方审查且本地提交已准备好；作者立即推送自己的分支并交接，不等固定时刻或另一方一起推送 |
| 更新已有 PR | 作者完成审查修复或吸收新 main，重新验证后新建提交并推送，重新请求检查当前 head |
| 合并 | 当前 PR 所需依赖已 DONE、当前 head 已审查、已吸收最新 main、检查通过；甲立即串行合并，不等待凑齐一批 PR |
| 拉取 | 远端已有新合入提交，且本端要启动/继续依赖该版本的任务；先检查工作区，再同步。不能盲目在有未提交改动的目录拉取 |
| 开始下一任务 | 常规任务满足第4.3节前置并同步main；甲的指定模块也可满足第4.4节提前开发条件后开工，但不解锁合并或集成。同一文件不得由并行任务同时写入 |
| 发布 | 必交功能在 main 集成验收通过、所需官方确认完成，甲才从已验证版本构建发布；乙收到真实地址后执行公网验收 |
| 等待 | 有明确未完成依赖，且没有已正式解锁任务、第4.4节可提前开发模块或可执行修复时，记录 WAITING/BLOCKED 与对应 PR；不按钟点反复轮询 |

只按真实依赖排序，不再要求“甲乙必须同批推送”或“一律等甲任务合完才合乙任务”。两个互不依赖的 PR 谁先准备好就先审、先合；甲仍是唯一合并者，一次只合一个。随后待合的 PR 必须根据更新后的 main 重新同步和验证。
